# Match each instruction to primary evidence

## 1. Interpret the evidence correctly

The following references establish existing behavior, APIs and constraints. The integration architecture, KIR, package protocols, evidence policies and test gates are proposed engineering work. Correctness of that new work requires the specified implementation evidence; a link to an upstream document does not supply a preservation theorem.

The upstream Kuiper commit is also present in the target fork. Kuiper source links below use `FStarLang/kuiper`. The F* extraction pin is the actual `QuasarRay/FStar` submodule used by the target repository; it is fork-source evidence, not mislabeled as official upstream documentation. Official F*/Pulse manuals supply the language-level context. Live manuals and API docs must be snapshotted/pinned in P0 before qualification.

## 2. Check claims at implementation time

For each primitive, record its source contract and extraction path, intended KIR meaning, target rule, preservation obligation and positive/negative fixtures. Cite the exact function/section and revision. If the official manual and pinned fork differ, explain the difference and use the actual pinned implementation for API calls; do not mix examples from unrelated versions.

A successful path needs all five forms of evidence: accepted source/caller obligations; representation checks; transformation relations under the selected policy; correct runtime/binding behavior; and qualification on the named hardware. None can be replaced by the roadmap's existence.
